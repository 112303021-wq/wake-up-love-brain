## 四、新問題（按嚴重度排序，編號接續 Q46）

### Q46【高】mock 的「無紅旗句」固定 15 句、題材離題，玩一兩次就能背，且文字特徵就能辨識
**證據**（實測 `s3.py`、讀 `personas.json mock_clean_lines`）：
- 每人格 `mock_clean_lines` 恰 15 句，且與劇情階段無關（天氣、貓、電影、學日文）：愛情騙子第 4 階催保證金時，clean 句可能是「我最近在學日文，你有學過什麼語言嗎？」。
- 文字特徵：愛情騙子 clean 平均 16 字 vs 紅旗句 29.7 字、clean 句 4／15 帶問號且無「寶貝」「～」；焦慮型 clean 16.1 vs 24.7 字。只憑「離題＋較短」就能高準確率判斷。
- 抽取決定於 `Random(f"{seed}|persona|stage|len(used_lines)") < 1/3`，種子 = 該局 `created_at`；同局可重現（優點），但**集合固定**：玩家重玩一次就記得全部 15 句。
- 「約 1/3」是每回合獨立機率，實際分布變異大：我跑的 60 局中「無紅旗句」比例不固定（部分局只有 1–2 句），誤檢舉鑑別力因局而異。
**為什麼重要**：誤檢舉懲罰是防刷分的核心（Q28 的修法），但 mock 的對照句太容易辨識，使用者測試的「過度警覺」指標將失真。真 LLM 上線前，所有成效數字都建立在這批 15 句上。
**建議**：clean 句必須與當前階段／上一句有語意關聯（例如正常關心、正常邀約、正常拒絕後的接話）；每人格至少 40 句並按階段分；長度與語氣和紅旗句對齊（用字數分布檢查）；每局保證 2–3 句（固定配額而非機率）。
**處理**：prompt（台詞資料）、後端 B（配額抽取）、研究（項目分析）。

### Q47【高】最後一則 NPC 訊息不能標紅旗，60% 的局 recall 因此被封頂
**證據**（實測 `v5.py`，5 人格 × 12 種子 = 60 局，每局用同一種離開句直到結束）：**36／60 局**，結束時最後一則 NPC 訊息帶紅旗但 `flag()` 回 400「flags are locked」。原因：`_send_locked` 在 `_advance` 設 `ended=True` 後仍呼叫 `_npc_turn` 補上最後一則 NPC 訊息，隨後局已結束，`flag` 被 Q21 的鎖擋住。
**為什麼重要**：玩家沒有機會標那一句，recall 分母卻包含它（`s3.py` oracle 在 avoidant／dependent 的 recall 為 88%／90%，分數因此低 5–9 分）。這使得「火眼金睛」門檻有 3／5 的人格近乎不可達，也讓研究指標（recall）有系統性低估。
**建議**：結束局前讓玩家可對最後一則訊息再標（例如局結束進入「覆盤前 30 秒」窗口），或把最後一則 NPC 訊息在計分時排除（`scoring.compute` 忽略結束後才出現的 NPC 訊息）。
**處理**：後端 B（流程）、後端 A（計分）。

### Q48【高】safety 規則對全新語料泛化極差：自傷召回 2%、暴力 17%、詐騙 36%，且遊戲內入戲轉帳被誤終局
**證據**：`s4.py` 218 句（見第二節）。代表性漏判：`我欲去死`、`想自我了斷`、`i wish i was dead`、`I want to unalive myself`、`我已經把遺書寫好了`、`我囤了很多藥`、`我撞牆撞到流血，這樣才覺得好一點`、`他掐著我的脖子`、`我爸又拿皮帶抽我`、`他叫我把存款轉到安全帳戶`、`我被騙走所有積蓄了`、`我今年才國一`、`我未滿18歲`、`請幫我暫停`、`你是不是用ChatGPT寫的`。誤終局：`被他打槍了好難過`、`我社死了好想消失`、`我不想活在別人的期待裡`、`工作壓力大到快撐不住了`（too_painful）、**入戲轉帳** `我剛剛匯了五萬到你的帳戶`、`我已經買了點數拍序號給你`（玩家在遊戲內對 NPC 說自己轉了錢，這正是遊戲要演的情節，卻被當成現實詐騙而終局）。
**為什麼重要**：第 5 輪把第 2 輪語料全轉成測試，造成「測試綠燈」的錯覺；規則本質是詞庫，沒有第二道網（LLM 分類器）。入戲轉帳誤終局會直接打斷核心玩法。
**建議**：(a) 目標改成「在盲測語料上量召回／誤判」，語料每輪輪替、不進訓練集（研究組維護 holdout）；(b) 加 LLM 風險分類器作第二道網（只在規則未觸發且文字含情緒／絕望線索時呼叫）；(c) real_scam 規則需區分「對象是 NPC（你）」與「對象是第三方」——句中有「給你／到你的帳戶」且發生在遊戲內，應視為入戲；(d) 台語、英文、委婉語各自建詞庫與正規化（`欲`、`袂`、`unalive`、`了斷`）。
**處理**：後端 A（規則）、研究（holdout 語料與目標）。

### Q49【高】fallback 台詞會取走「真紅旗句」卻不帶紅旗，玩家標對反被扣分
**證據**（實測 `v4.py`，LLM 一直失敗）：第一則 NPC 訊息是 fallback，文字為「寶貝早安～今天有想我嗎？遇到你我覺得自己真的好幸運❤️」，這是愛情騙子階段 1 的 `fast_intimacy` 紅旗句，但 `red_flags=[]`。玩家標它 → `correct=False`、結算 `false_positives=1`、`detect_score=0`。`fallback_output` 從 `persona.lines[stage]`（含所有紅旗句）取句，一律不帶紅旗。連續失敗時 4 回合內取到 4 句不同的紅旗台詞，全部無旗。
**為什麼重要**：LLM 暫時失敗（Q31 的拒答路徑也走 fallback）時，玩家做對卻被罰；而且 Q8 的輸出過濾誤殺（Q56）會讓 fallback 被觸發得更頻繁。
**建議**：fallback 只用無紅旗句（`mock_clean_lines` 或帶 `no_flag` 的句子）；或沿用該台詞原本的 mock 紅旗標記；fallback 訊息在計分時排除（`m.get("fallback")` 不計入 recall／precision 分母，也不計誤檢舉）。
**處理**：後端 B。

### Q50【高】舊存檔認領：知道 ID 的人可搶先拿 token，原主被鎖在外面
**證據**（實測 `v3.py`）：建立一個沒有 `token_hash` 的舊存檔 `legacy0001`；(1) 無憑證 `GET /api/profile?player=legacy0001` 回 200 並讀到暱稱；(2) 攻擊者 `POST /api/nickname {player:'legacy0001'}` → 200 並取得 `token`；(3) 原主再送任何寫入 → 401「token required」。目前 `saves/` 真實存在 3 個這種舊檔（`phnf3me8rsf`、`py1973q2nco`、`pyxrse7rgg3`）。
**為什麼重要**：契約寫「認領前任何知道 ID 的人都可讀寫（遷移期限制）」，但沒有遷移期結束的機制。舊 ID 是 localStorage 隨機字串，已在使用者瀏覽器與（可能）截圖／紀錄中出現。
**建議**：上線前一次性遷移：對所有舊檔簽發 token 並由管理者交付，或直接封存（改名 `.legacy`）並要求重建；不要讓「建立型路由」默默認領既有玩家。
**處理**：後端 B。

### Q51【中】自由輸入的自然回覆被分類成 neutral／brain，合理玩法拿不到滿分
**證據**（實測 `scoring.classify_text`）：「謝謝你，我也覺得跟你聊天很開心」→ neutral；「好呀，那我們週末再約，慢慢認識」→ neutral；「嗯嗯我了解，我們先這樣安排」→ **brain**（`嗯嗯` 在弱順從詞表）。對正常訊息的得體回覆最多得 neutral（行為分 0、被騙指數算半個順從），所以 oracle 的行為分上限約 62。
**為什麼重要**：與 Q47 疊加，合理玩法的最高分取決於運氣；且自然回覆被當作「順從」會觸發教練責備（若對方有紅旗）。
**建議**：新增 `normal` 類（對無紅旗句的得體回應），計入行為分的正向項；弱順從詞（嗯嗯、好呀）只在對方有紅旗時才算 brain。
**處理**：後端 A。

### Q52【中】速率限制可被拿來攻擊別人，也可被輪換 ID 繞過；GET 存在性 oracle
**證據**（實測 `v3.py`，`GAME_RATE_PER_MIN=60`）：
- `rate_limit(pid)` 在授權之前執行且以「玩家 ID」計數。攻擊者用目標 ID 送 70 個**無 token**請求（56 個 401、14 個 429）後，持有正確 token 的受害者請求回 **429 rate_limited**。
- 同一個客戶端輪換 ID：200 次 `/api/start` 全部成功、建立 200 個檔，沒有 IP／全域限制。
- 存在性 oracle：`GET /api/profile?player=` 對存在的玩家回 401、不存在回 200（空資料）→ 攻擊者可確認某 ID 是否存在後再針對性灌流量。
**建議**：速率限制先看授權結果（未授權請求不計入受害者額度，改以來源 IP 與全域計）；對不存在與無權限回同一種錯誤碼；建檔路由加 IP 級限制與全域建檔速率。
**處理**：後端 B。

### Q53【中】配額可被灌爆，且 admin header 的非 ASCII 值造成 500
**證據**（實測 `v3.py`）：
- `GAME_MAX_PLAYERS` 設為「現有數量＋20」，攻擊者以 30 個隨機 ID 呼叫 `/api/start` 後，真正的新使用者回 **429 quota_exceeded**。預設 2000 只要 2000 個請求（上一點的輪換 ID 無限制）。
- 設定 `GAME_ADMIN_TOKEN` 後，送 `X-Admin-Token: 密碼`（非 ASCII）→ `hmac.compare_digest` 拋 `TypeError: comparing strings with non-ASCII characters is not supported` → 500。無法繞過授權，但可探測管理者機制是否啟用，也代表錯誤處理不完整。
- 管理者 token 預設值：未設定環境變數時 admin 機制關閉（送 `admin` 無效）；設為空字串也關閉。這點正確。
**建議**：建檔配額分「每 IP」與「全域」，並對超額保留一部分名額給已知來源；admin 比對改成 `hmac.compare_digest(a.encode(), b.encode())`。
**處理**：後端 B。

### Q54【中】safety 狀態仍是 per-session：切人格或 reset 後立即繼續（第 1 輪 Q15 遺留）
**證據**：第 5 輪 changelog 自述「未做：safety 狀態跨人格」。實測 self_harm 終局後其他人格可直接 start／send；`reset` 重置 resume 預算（`v5.py`：reset 後 pause 可再 resume 3 次）。
**為什麼重要**：高風險類別（self_harm、real_violence、minor）終局後沒有任何跨局的處置；minor 觸發後換個人格就繞過。
**建議**：高風險類別在 profile 層設 `safety_hold`（例如 10 分鐘內只顯示資源頁，或需明確確認）；minor 觸發後要求重新確認年齡才可繼續。
**處理**：後端 A／B、研究（處置流程）。

### Q55【中】教練仍稱讚「對正常句的拒絕」，與計分的過度拒絕扣分互相矛盾（Q40 未解）

**建議**：對無紅旗句的拒絕改為中性提示（「這句其實可以正常聊聊，不是每句都要拒絕」），不稱讚；教練與計分共用同一個「對方有無紅旗」判定。
**處理**：後端 A。

### Q56【中】輸出過濾有誤殺與繞過
